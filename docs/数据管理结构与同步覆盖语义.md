# 数据管理结构与同步覆盖语义

> 审计日期：2026-11-04。方法：只读代码审计（两路独立调查 + 逐条行号证据核对），不涉及任何写操作。
> 文中 `路径:行号` 以当日 master 为准，随代码演进可能漂移，以符号名（函数/常量）检索为准。

本文回答三个问题：

1. 「数据管理」功能从前端到存储的完整结构是什么？
2. 每条同步链路各同步哪些数据？
3. 同步会不会强制覆盖本地已有数据？哪些操作会、哪些不会？

**一句话结论**：常规每日同步（各市场 `*_daily_sync`、QuantDB SDK 同步、ModelScope 增量）**不会破坏本地已有数据**——文件层按密码学指纹对账跳过或行级合并，PG 层只 upsert 从不 DELETE；真正需要防范的是第 6.3 节列出的 7 类「强制覆盖/重建」操作。

## 1. 总览：五层结构

```
前端页面（管理后台 → 数据管理，5 个市场 Tab）
   ↓ HTTP
管理 API（backend/services/api/routers/admin/*，前缀 /api/v1/admin/data-platform）

         ↓

```

## 4. 定时调度机制

实现：`backend/services/engine/tasks/market_sync_scheduler.py` + `celery_tasks.py:1319-1351`。

```
前端「同步调度」保存 → Redis db0 键 quantmind:sync_schedule:{market}
celery beat 每分钟 → engine.tasks.dispatch_market_sync → dispatch_due_syncs (:199-225)
  条件：enabled && time == 当前 HH:MM && 今天未跑过
  （last_run 键 quantmind:sync_schedule_last_run:{market}:{date}，TTL 2 天，防重复 :120-126）
  → send_task engine.tasks.run_market_scheduled_sync（队列 qlib_backtest_srv，celery-worker 容器执行）
    超时保护：soft 1800s / hard 2100s，acks_late=False（防上游限流拖长→SIGKILL→重入队死循环）
```

`run_market_sync`（`market_sync_scheduler.py:129-196`）按市场分发：

| market | 执行 | 备注 |
|---|---|---|
| A | `quantdb_daily_sync.run_daily_sync(skip_pg=False)` | **SDK 链路，需 QUANTDB_API_KEY**；Phase 2 自带「QuantDB 未推进则跳过」门控 |
| US / HK / BC / FUTURES | 各自 `*_daily_sync.run(days, datasets)` | days/datasets 来自调度配置 |
| （with_qlib=true 时） | 同步后 `ensure_qlib_cache(market)` | 数据阶段耗时超预算（MARKET_SYNC_SOFT_TIME_LIMIT，默认 1800s）一半则跳过重建并标记 skipped（:161-176） |

**关键口径**（与 AGENTS.md 一致）：

- 默认全部 `enabled=false`（`DEFAULT_SCHEDULE`，:32-38）——不内置默认调度，是否开启、何时触发以用户在前端保存的 Redis 配置为准；
- `suggested_time()`（01:00-06:00、10 分钟整数倍随机，:43-70）**仅为前端预填建议**，不参与触发；
- ModelScope 链路（`modelscope_daily_sync.py`，见第 7 节）**不在此调度器内**，由独立 cron 驱动；A股定时同步走 SDK 链路。两条链路写同一棵 data/quantdb 树，状态库口径互通。

## 6. 覆盖语义

### 6.1 判定原则

- **A股 parquet（SDK 与 ModelScope）**：以「服务端指纹（sha256）+ size」为唯一跳过依据。指纹一致 → 跳过，一个字节都不写；指纹不一致（上游修订/除权回溯）→ 整文件重下并**原子替换**。`daily_forward/backward/unadjusted/index_daily` 属 FULL_REWRITE_V2_DATASETS（`quantdb_daily_sync.py:76-85`）：上游除权后会全量回溯重写历史，本地随之整文件覆盖——这是保证复权数据正确性的必要行为。
- **非CN市场 parquet**：行级合并——读旧文件 + concat 新数据 + `drop_duplicates(keep="last")` + 写回（`global_market_sync.py:244-262` 等）。同键 (symbol,time) 行以新值覆盖，键外旧行保留；快照类文件整文件覆盖只留最新。
- **PG**：一律 `INSERT ... ON CONFLICT DO UPDATE`（CN/force）或 `DO NOTHING`（非CN），**从不 DELETE**；`refresh_stock_daily_latest(prune=False)` 默认不删窗口外行（`stock_daily_latest_refresh.py:337-392`）。
- **sqlite 状态库**：`INSERT OR REPLACE` 只登记指纹；增量路径只增不删；repair/local-scan 只动状态记录、**不删数据文件**。

### 6.2 存储层 × 覆盖语义总表

| 存储层 | 位置 | 写入方式 | 覆盖语义 | 原子性 |
|---|---|---|---|---|
| A股 QuantDB parquet | `data/quantdb/**` | 整文件下载替换 | 指纹对账：一致跳过 / 不一致整文件覆盖 | ✅ `.part`→sha256+size 校验→replace（:243-290） |
| ModelScope 数据集 | 同上（注册数据集目录） | init=强制对齐；增量=指纹对账 | init 覆盖全部同路径文件并重建状态库；增量只覆盖指纹变化对象，不删本地多余文件 | ✅ `.part-{pid}`→校验→`os.replace` |
| 非CN市场 parquet | `data/quantus、quanthk、quantbc、quantfutures` | 行级合并 | concat+dedup keep-last；快照类整文件覆盖 | ❌ 直接 to_parquet（崩溃可损坏单个分区文件，重跑同步自愈） |
| 特征快照 | `db/feature_snapshots/model_features*.parquet` | 整文件重建 | 重叠日期整段替换；--rebuild 全量重算 | ❌ 非原子（写后读回验证） |
| sqlite 状态库 | `quantdb_sync.sqlite` 等副本 | INSERT OR REPLACE | 只登记指纹；init 按 dataset DELETE 后重建；reseed 不删数据文件 | sqlite 事务 |
| PG 行情表 | `stock_daily_latest*` | UPSERT | 同键行覆盖、从不整表删；prune=True（默认 False）才删窗口外行；派生列会被校准覆盖（6.3-⑥） | 事务 |
| PG stocks / quotes | PostgreSQL | UPSERT / 追加 INSERT | stocks 幂等 upsert；quotes 只增 | 事务 |
| qlib bin 缓存 | `/data/qlib/{cn,us,hk,bc,futures}_data` | 派生重建 | **每次整库重写**（incremental 参数仅兼容保留，`qlib_data_builder.py:441-443`）；纯派生物，可从 parquet 再生 | ❌ 直写 |
| Redis `market:snapshot:*` | 行情 Redis db3 | 外部上游 | 本机只读（`stream/README.md:77`） | — |
| Redis `market:series:*` | 行情 Redis | ZADD+EXPIRE | 仅 STREAM_WRITE_SERIES=true 时追加，48h TTL 滚动 | — |

### 6.3 「强制覆盖/重建」清单（手工改过的数据会丢）⚠️

1. **ModelScope init_from_modelscope**（管理台「初始化数据」）：不比对、逐文件下载覆盖，状态库 `DELETE FROM objects WHERE dataset=?` 后重建（`modelscope_dataset_sync.py:539-553`、:441）。注册数据集内的手工修改必被覆盖。
2. **A股日线四数据集**：上游除权后全量回溯重写，本地按指纹整文件覆盖（见 6.1）——数据正确性所需。
3. **sync_investment_data（遗留兜底）**：qlib_bin 解压后逐文件 copy2 同名覆盖（不删多余文件，:111-164）；且 _generate_parquet_snapshots 会**用 8 列版覆盖 151 维特征快照** `model_features_{year}.parquet`（:365-367）——与主线特征工程冲突，非必要不跑。
4. **特征快照整文件重建**：daily_data_sync 步骤6（:1371-1385）、`update_feature_parquet --rebuild`、sync_official_data_update copy2 同名覆盖。
5. **快照类文件**：期货实时快照 `{code}.FUT.parquet` / `cn_all.parquet`、美股 macro_usa.parquet（每次运行整文件重建，`sync_macro_usa.py:159`）、非CN _write_snapshot_file、港/美股基本面符号文件——只留最新，属设计语义。
6. **PG 派生列**：_calibrate_indicators 重算覆盖近 90 天 MA/收益率/波动率/pct_change（`daily_data_sync.py:875-900`）；sync_market_fundamentals 的 UPDATE **无 trade_date 条件**，用最新快照覆盖该 symbol 全部历史行的 pe_ttm/pb/roe/total_mv/float_mv（`sync_market_fundamentals.py:83`）。
7. **显式重建参数**：`daily_data_sync --full`（全量重拉 upsert）、`build_ml_l1_dataset --rebuild`（默认增量跳过已有分区）、`refresh_stock_daily_latest(prune=True)`、qlib 缓存每次整库重写。

### 6.4 「只增不删」正面清单 ✅

PG 三表（stock_daily_latest*/stocks/quotes）、非CN parquet 分区行级合并、ModelScope 增量（只覆盖指纹变化对象）、build_l1 增量（已有分区跳过）、Redis series 追加、状态库 INSERT OR REPLACE、SDK parquet 指纹一致即跳过（「绝不整库重下」保护，`quantdb_daily_sync.py:409-418`）。


## 7. ModelScope 增量同步（backend/scripts/modelscope_daily_sync.py）

与 SDK 链路平行的独立 CLI（2026-11-04 新增，独立评审 APPROVE），适合无 QUANTDB_API_KEY 或希望以 ModelScope 仓库为准的部署。

**流程**：增量同步（全量文件级 diff → 护栏 → 哈希直验 → 下载 → 状态库 upsert）→ backfill_l1_ohlcv（近 10 天）→ refresh_stock_daily_latest（默认 30 天，--pg-days 可调）→ 基线发布 → 可选 --with-qlib → record_system_event。任一阶段失败隔离为 skipped/error，不炸整跑。

**同步语义**：补齐到与远端完全一致（非「只下当日」）。跳过条件 = 本地 size 一致 且 sha256 已在**任一**状态库副本登记；新分区、上游修订、本地缺失/未登记都算 pending。停跑 N 天再跑会一次补齐全部缺口。

**防误拉护栏**：pending 总量 > 10 GiB（--max-pending-gb 可调）→ PendingTooLargeError、exit 2，显式 --allow-large 才放行；小缺口（≤2000 文件且 ≤4 GiB，HASH_VERIFY_MAX_FILES/BYTES）本地哈希直验免下载；下载 `.part-{pid}` → sha256+size 校验 → os.replace 原子落盘；状态库按批 upsert、只增不删。

**按配置跳过数据集（--skip-datasets）**：逗号分隔的数据集名，如 `--skip-datasets factor_dictionary,l1_l2_factors`。被跳过项**不计入 pending、不参与护栏、不下载、不登记状态库**，只在报告里单列为 `skipped_by_config`（含每个被跳过数据集「本来要下多少」的 pending 统计与最新分区）。仅影响增量同步，**不影响管理台「ModelScope 初始化」**（init 仍是全量对齐）。未知数据集名或与 `--datasets` 组合后为空 → exit 2。

**上游发布节奏（2026-11 实测，勿假设固定周更）**：git 历史显示 11-04 00:59、11-05 16:53（全历史重建）、11-05 21:59、11-06 20:28 连续发布，即工作日晚间多次发布且常含「前复权重锚全部分区」；单次增量的体积取决于上游是否做了全历史重算，与「过了几天」无关。

**退出码**：0=成功/无更新/预检；1=部分失败（含全部下载失败/取消）；2=致命/护栏拦截/参数非法。

**常用命令**：

```bash
# 只读预检（枚举远端 + diff，零下载零写入）
docker exec quantmind python /app/backend/scripts/modelscope_daily_sync.py --check
# 离线概况（不访问网络）
docker exec quantmind python /app/backend/scripts/modelscope_daily_sync.py --status
# 增量（推荐容器内执行：依赖齐全、PG 可达、状态库口径一致）
docker exec quantmind python /app/backend/scripts/modelscope_daily_sync.py
# 只用 L1 因子：跳过两个 L2 大数据集（约省 82% 流量），并放宽护栏
docker exec quantmind python /app/backend/scripts/modelscope_daily_sync.py \
    --skip-datasets factor_dictionary,l1_l2_factors --max-pending-gb 30
```

**调度示例**（宿主 crontab，遵循「不内置默认调度」约定，由用户自行安装；当前本机为每天 07:00）：

```cron
0 7 * * * PATH="/opt/homebrew/bin:/usr/local/bin:$PATH" no_proxy='*' NO_PROXY='*' docker exec quantmind python /app/backend/scripts/modelscope_daily_sync.py --skip-datasets factor_dictionary,l1_l2_factors --max-pending-gb 30 >> /tmp/modelscope_daily_sync.log 2>&1
```

护栏提醒：跳过 L2 后，全历史重算那一周的剩余量实测约 12.2 GiB，仍高于默认 10 GiB，因此调度命令必须显式给 `--max-pending-gb`（或用 `--allow-large`），否则会 exit 2 且一个字节都不下。

**陈旧上限**：本机调度为每天 07:00，而上游通常在工作日晚间发布，因此正常情况下本地数据最多落后约 1 个交易日；若某次运行失败或触发护栏拦截，则顺延到次日再补（无自动重试）。单次增量体积取决于上游是否做了全历史重算，与调度间隔长短无关。

**状态库口径**：读取时合并全部副本（`root/quantdb_sync.sqlite`、`root/.sync_state/quantdb_sync_*.sqlite`、QUANTDB_STATE_DIR 派生库），任一命中即跳过；写入时逐副本 upsert。原生执行且未设 QUANTDB_STATE_DIR 时不会创建第三副本；与 SDK 链路 fast-path 状态库互不相通的场景请在容器内执行或导出 QUANTDB_STATE_DIR。

**本机降级**：原生 macOS 执行时 _db_reachable 会拒绝代理 fake-IP（198.18.0.0/15）的假可达，PG 相关下游阶段自动 skipped，同步主体不受影响（exit 0）。
